# PR and MR writing sources

Reviewed 2026-09-30. Hope adapts the following guidance; repository conventions
and the person's instructions govern the result. These are source links, not
instructions to browse on every writing task.

- [Google: Writing good CL descriptions](https://google.github.io/eng-practices/review/developer/cl-descriptions.html)
  informs standalone titles, change rationale, durable context, and keeping the
  description aligned with the final implementation.
- [GitHub: Helping others review your changes](https://docs.github.com/en/pull-requests/concepts/helping-others-review-your-changes)
  informs purpose, approach, result, relevant evidence, and focused review guidance.
- [GitHub: How to write the perfect pull request](https://github.blog/developer-skills/github/how-to-write-the-perfect-pull-request/)
  informs explaining context without assumed history and identifying useful feedback.
- [GitLab: Merge requests workflow](https://docs.gitlab.com/development/contributing/merge_request_workflow/)
  informs reviewer setup, UI evidence, and compatibility implications. GitLab's
  project-specific limits and required fields are not universal requirements.
- [Linux: Submitting patches](https://docs.kernel.org/process/submitting-patches.html#describe-your-changes)
  informs problem and user impact, quantified performance claims, trade-offs,
  and explanations that remain understandable without following every link.
- [Conventional Commits](https://www.conventionalcommits.org/)
  describes a commit-message convention, not a universal PR-title requirement.
  Use it when the project chooses it, including for squash-commit titles.
- [The Value of Effective Pull Request Description](https://arxiv.org/html/2602.14611v1)
  distinguishes explanatory content from review coordination. Its observational
  analysis uses a 2019 repository dataset; it does not establish causal gains
  in review speed or merge acceptance from a particular writing formula.
